# Phase 2.1 — DI Context Split

## Problem

`InfrastructureContext` (120 lines) mixes: HTTP infra, Prisma, all repos, JWT, crypto, factories, application services, UoW.
`ApplicationContext` (61 lines) mixes: client/user/project commands, controllers, middleware — will double after Phase 2.

Both files will be unreadable after Phase 2 is complete. Maintenance pain: adding a new handler requires hunting through a 200-line file to find the right section.

---

## Target Structure

```
src/contexts/
  infrastructure/
    PersistenceContext.ts   — Prisma + all repos + UoW
    HttpContext.ts          — Express, HttpServerFactory, routers, ErrorHandler
    AdaptersContext.ts      — JWT, crypto, bcrypt, UUID, logger, ServerConfig + port bindings
  application/
    ClientContext.ts        — client commands + queries + controller + middleware + auth services + factories
    UserContext.ts          — user commands + queries + controller + middleware + auth services + factories
    ProjectContext.ts       — project commands + queries + controller + shared app services
  ServiceContext.ts         — (unchanged)
  ServiceContextBuilder.ts  — (unchanged)
```

## bootstrap.ts After Split

```ts
new ServiceContextBuilder(container, [
  // Infrastructure (no inter-dependencies between these three)
  new PersistenceContext(),
  new AdaptersContext(),
  new HttpContext(),
  // Application (depend on infra bindings)
  new ClientContext(),
  new UserContext(),
  new ProjectContext(),
]).build()
```

> Inversify resolves lazily at `container.get()` time, so registration order doesn't matter for correctness. Logical grouping above makes intent clear.

---

## Migration Steps

1. Create `src/contexts/infrastructure/` and `src/contexts/application/` dirs
2. Create the 6 new context files — copy-paste bindings from existing, no logic changes
3. Update `bootstrap.ts` — replace 2 contexts with 6
4. Delete `ApplicationContext.ts` + `InfrastructureContext.ts`
5. `pnpm typecheck` — verify no missing bindings

**No handler/repo/service code changes.** Pure reorganization of DI wiring. All imports in the new context files point to the same places they did before.

---

## Notes

- `GetClientProjectsHandler` currently lives in ApplicationContext — move to `ClientContext`
- `SchemaBuilderService` is used by both `ProjectContext` (ProjectField) and `UserContext` (UpdateUserField) — bind in `ProjectContext`, it's a singleton so both contexts resolve the same instance
- After Phase 2 adds ~19 handlers, `ProjectContext` will be ~25 bindings — still manageable as one file
- Do NOT further split by command vs query within a context — overkill at this scale
