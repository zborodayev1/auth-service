# Phase 2.12 — Email Change Missing Session Revocation

Password change revokes all sessions. Email change does not. Both operations require password confirmation — same authentication bar, different security outcome.

---

## Asymmetry

| Handler | Requires password | Revokes sessions |
|---------|------------------|-----------------|
| `ChangeClientPasswordHandler` | ✓ | ✓ `revokeAllByClientId` |
| `ChangeClientEmailHandler` | ✓ | ✗ |
| `ChangeUserPasswordHandler` | ✓ | ✓ `revokeAllByUserId` |
| `ChangeUserEmailHandler` | ✓ | ✗ |

After email is changed, all sessions created under the old email remain valid and can continue issuing requests. If the account email is used for identity (e.g., future email verification, recovery flows), this creates a window where a session is associated with a now-stale identity.

---

## Checklist

- [ ] `ChangeClientEmailHandler` — inject `ClientSessionRepository`, revoke all sessions atomically with the email save inside `UnitOfWork`
- [ ] `ChangeUserEmailHandler` — inject `UserSessionRepository`, revoke all sessions atomically with the email save inside `UnitOfWork`
- [ ] Verify both handlers use `unitOfWork.execute` to wrap save + revoke together (same pattern as `ChangeClientPasswordHandler`)
- [ ] Decide: should the current session (the one making the request) also be revoked, forcing re-login? Or keep it alive (less disruptive)? Document the decision.
