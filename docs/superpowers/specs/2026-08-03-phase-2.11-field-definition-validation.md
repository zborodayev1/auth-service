# Phase 2.11 — ProjectField Cross-Field Validation Gaps

`AddProjectField` and `UpdateProjectField` validators treat each field independently. No rules enforce coherence between `type`, `enumValues`, and `defaultValue`. Two categories of broken state result.

---

## Gap 1 — `type=enum` with empty `enumValues`

`AddProjectFieldSchema` accepts `type: 'enum'` with `enumValues: []` — no minimum length on the array, no conditional check.

**What happens:**
- Field is stored in DB with `type=enum`, `enumValues=[]`
- `SchemaBuilderService.build()` calls `z.enum([] as [string, ...string[]])` — TypeScript cast hides the empty array, runtime produces a schema that rejects every value
- If field is `required: true` → every `RegisterUser` for that project fails (ZodError → 500, see 2.7.1)
- If field is optional → `UpdateUserField` for that field always fails (ZodError → 500)
- No recovery path: field cannot have a valid value. Only deletion removes the broken state.

**Checklist:**
- [ ] When `type === 'enum'`, require `enumValues.length >= 1` in `AddProjectFieldSchema`
- [ ] Same rule in `UpdateProjectFieldSchema`
- [ ] Consider minimum 2 values for enum (single-value enum is semantically useless)

---

## Gap 2 — `defaultValue` not validated against `type`

`defaultValue` is stored as a raw string with no type coherence check. `SchemaBuilderService.parseDefault` then tries to coerce it:

| type | `parseDefault` | bad `defaultValue` | result |
|------|---------------|-------------------|--------|
| `number` | `Number(raw)` | `"abc"` | `NaN` stored as default |
| `date` | `new Date(raw)` | `"not-a-date"` | `Invalid Date` default |
| `enum` | returns raw string | `"invalid_choice"` | value outside enum stored as default |
| `boolean` | `raw === 'true'` | anything not `"true"` | silently defaults to `false` |

When Zod applies a bad default during `RegisterUser`, the corrupted value is serialized via `String(validated[f.name])` and written to `UserFieldValue`. No error is thrown — data is silently wrong.

**Checklist:**
- [ ] For `type=number`: validate `defaultValue` is a finite parseable number (e.g. `!isNaN(Number(defaultValue))`)
- [ ] For `type=date`: validate `defaultValue` produces a valid date (`!isNaN(new Date(defaultValue).getTime())`)
- [ ] For `type=enum`: validate `defaultValue` is one of `enumValues`
- [ ] For `type=boolean`: validate `defaultValue` is `"true"` or `"false"` exactly
- [ ] For `type=string`: no constraint on `defaultValue`
- [ ] Apply same rules in both `AddProjectField` and `UpdateProjectField` (validator or handler level)
