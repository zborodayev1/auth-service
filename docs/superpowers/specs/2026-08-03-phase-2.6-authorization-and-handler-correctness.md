# Phase 2.6 — Authorization Gap + Handler Correctness

Two independent bugs found in code review. Neither requires architectural changes.

---

## 2.6.1 — Authorization Gap in Project Field Operations

**Problem:** All project CRUD, API key, and user-admin endpoints correctly pass `clientId` and verify ownership via `ProjectAccessService`. Four field endpoints do not.

Any authenticated client who knows a project UUID can read, add, update, and delete fields in another client's project.

| Endpoint | Status |
|----------|--------|
| `GET /projects/:projectId/fields` | ❌ no ownership check |
| `POST /projects/:projectId/fields` | ❌ no ownership check |
| `PATCH /projects/:projectId/fields/:fieldId` | ⚠️ checks `field.projectId === command.projectId` only |
| `DELETE /projects/:projectId/fields/:fieldId` | ⚠️ checks `field.projectId === command.projectId` only |

The partial check on update/delete prevents cross-project field tampering via fieldId spoofing, but does not prevent a client from operating on a project they don't own.

**Root cause:** `AddProjectFieldCommand`, `UpdateProjectFieldCommand`, `DeleteProjectFieldCommand` have no `clientId` field. `GetProjectFieldsQuery` has no `clientId` field. The controller methods (`addField`, `updateField`, `deleteField`, `getFields`) never pass `req.auth.clientId` to their commands.

---

### Fix

**1. Add `clientId` to all four commands/queries:**

```ts
// AddProjectFieldCommand
export class AddProjectFieldCommand {
  constructor(
    public readonly clientId: string,  // add
    public readonly projectId: string,
    // ...rest unchanged
  ) {}
}

// UpdateProjectFieldCommand
export class UpdateProjectFieldCommand {
  constructor(
    public readonly clientId: string,  // add
    public readonly projectId: string,
    // ...rest unchanged
  ) {}
}

// DeleteProjectFieldCommand
export class DeleteProjectFieldCommand {
  constructor(
    public readonly clientId: string,  // add
    public readonly fieldId: string,
    public readonly projectId: string,
    public readonly force: boolean,
  ) {}
}

// GetProjectFieldsQuery
export class GetProjectFieldsQuery {
  constructor(
    public readonly clientId: string,  // add
    public readonly projectId: string,
  ) {}
}
```

**2. Add ownership check in each handler:**

All four handlers need `ProjectAccessService` injected and called first:

```ts
// AddProjectFieldHandler.execute()
await this.accessService.verifyByProjectId(command.clientId, command.projectId)
// ... rest of handler unchanged

// UpdateProjectFieldHandler.execute()
await this.accessService.verifyByProjectId(command.clientId, command.projectId)
// ... remove the manual field.projectId !== command.projectId check (redundant after this)

// DeleteProjectFieldHandler.execute()
await this.accessService.verifyByProjectId(command.clientId, command.projectId)
// ... remove the manual field.projectId !== command.projectId check (redundant after this)

// GetProjectFieldsHandler.execute()
await this.accessService.verifyByProjectId(query.clientId, query.projectId)
// ... rest unchanged
```

**3. Update controller to pass `clientId`:**

```ts
// ProjectController.addField
new AddProjectFieldCommand(req.auth.clientId, projectId, body.name, ...)

// ProjectController.updateField
new UpdateProjectFieldCommand(req.auth.clientId, projectId, fieldId, ...)

// ProjectController.deleteField
new DeleteProjectFieldCommand(req.auth.clientId, fieldId, projectId, force)

// ProjectController.getFields
new GetProjectFieldsQuery(req.auth.clientId, projectId)
```

**4. DI:** `ProjectAccessService` is already bound in the context. Just inject it into the three handlers that are missing it (`AddProjectFieldHandler`, `UpdateProjectFieldHandler`, `GetProjectFieldsHandler`). `DeleteProjectFieldHandler` does not currently inject it either.

## 2.6.2 — Handler Deduplication + Spurious Schema Cache Invalidation

### Duplicate handlers

`GetProjectUserHandler` and `GetProjectUserFieldsHandler` perform identical DB work:

```
1. accessService.verifyByUserId(clientId, userId)   → user + project
2. fieldsService.getFieldsWithValues(userId, projectId) → fields[]
```

`GetProjectUserFields` returns `{ fields }`. `GetProjectUser` returns `{ id, email, projectId, createdAt, fields }` — a strict superset.

The endpoint `GET /projects/:projectId/users/:userId/fields` can be removed entirely. Any consumer that wants only fields from the full user object can destructure client-side. Two endpoints doing the same 3 DB queries is unnecessary.

**Fix:** Delete `GetProjectUserFieldsHandler`, `GetProjectUserFieldsQuery`, remove the route and controller method.

```ts
// Remove from ProjectRouter:
router.get('/:projectId/users/:userId/fields', authenticate, c.getUserFields.bind(c))

// Remove from ProjectController:
// - getUserFields method
// - GetProjectUserFieldsHandler injection
// - GetProjectUserFieldsQuery import
```

Delete files:
- `src/application/queries/project/GetProjectUserFields/GetProjectUserFieldsHandler.ts`
- `src/application/queries/project/GetProjectUserFields/GetProjectUserFieldsQuery.ts`

Remove bindings from DI context.

**Note:** If a future SDK needs a fields-only endpoint for bandwidth reasons, add it back then. Don't keep dead weight now.

---

### Spurious schema cache invalidation

`UpdateProjectUserFieldHandler` (admin updates a user's field value) calls `schemaBuilder.invalidate(user.projectId)` after saving.

Updating a field **value** does not change the project field **schema**. The schema cache contains `ZodObject` instances built from `ProjectField` definitions — none of which changed.

Compare: `UpdateUserFieldHandler` (user self-update) correctly does **not** call `schemaBuilder.invalidate()`.

Effect: every admin field value update forces the next `RegisterUser` to rebuild and re-cache the Zod schema from DB. Wasteful and inconsistent.

**Fix:** Remove the `schemaBuilder.invalidate()` call and `SchemaBuilderService` injection from `UpdateProjectUserFieldHandler`:

```ts
// Remove:
@inject(SchemaBuilderService) private readonly schemaBuilder: SchemaBuilderService,

// Remove from execute():
this.schemaBuilder.invalidate(user.projectId)
```
